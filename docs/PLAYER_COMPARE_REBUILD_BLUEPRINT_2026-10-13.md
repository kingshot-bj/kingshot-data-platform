# EagleEye プレイヤー比較 再構築設計書

作成日: 2026-10-13  
対象: `/player/compare`, `/api/player-compare`, `/api/player/refresh`  
調査対象: `main`（調査時点）

## 1. 目的

既存の戦力カードを改造して秘境の試練に見せるのではなく、KvKの集結主候補を実データで見比べる専用画面として作り直す。

- 上段: 秘境の試練・総合ランキング比較を大きく表示
- 下段: 6エリアのランキングを小さなカードで表示
- 2〜4人を比較。スマホは2列×3段、広い画面では3列を基本とする
- プレイヤーごとの色を全カードで統一する
- カウントアップ、リングアニメーション、火花・発光などの演出は維持する。ただし `prefers-reduced-motion` を尊重する
- 説明文は最小限。未取得値は推測せず「未取得」とする

## 2. 画面構成

### A. ヘッダー
- 「プレイヤー比較」
- 比較人数、最終取得日時、更新状態
- 「再読み込み」「最新データで比較」
- 更新中は段階・対象人数・経過時間を明示

### B. 総合ランキングカード（最上段・主役）
- ラベル: 「秘境の試練」
- 2〜4人の実スコアを円形ゲージで比較
- スコア、順位、データ取得時刻を表示
- スコア差は実スコア同士の差として表示できる場合のみ表示
- 順位しか存在しない場合は順位を表示し、順位をスコア扱いしない
- 総合ランキングのスコアが取得できない場合、他の項目から独自の合算点を作らない

### C. 6エリアカード
スマホ: 2列×3段。PC: 3列を基本とする。

| 表示名 | API/board候補 | UI要件 |
|---|---|---|
| 闘技場 | `coliseum` | 実スコア・順位・取得時刻 |
| 生命の森 | `forest_of_life` | 実スコア・順位・取得時刻 |
| 水晶鉱山 | `crystal_cave` | 実スコア・順位・取得時刻 |
| 知識の枢軸 | `knowledge_nexus` | 実スコア・順位・取得時刻 |
| 溶岩要塞 | `molten_fort` | 実スコア・順位・取得時刻 |
| 輝光の塔 | `radiant_spire` | 実スコア・順位・取得時刻 |

エリアごとに、同じ指標・同じ単位で比較できると確認できた項目だけを描画する。カード内でスコアが未取得でも、他のカードまで非表示にしない。

### D. 追加ランキング（第2段階）
- EagleEyeが扱う全26ランキングから比較項目を選択・解除できる既存要件は維持する
- ただし総合＋6エリアの主表示を崩さず、追加項目は折りたたみの選択UIに分ける
- 今回の初期実装では、データの実在を確認できていない項目を仮表示しない

## 3. コード監査で確認できた事実

### 現行API/UI
- `src/index.js` の `handlePlayerCompareApi()` は、プレイヤー行と現在の観測payloadを取得している
- 現行比較APIの返却値は `rankings: null`, `rankingsExpected: false`, `rankHistory: []` で固定されている
- そのため、現行の比較APIだけでは総合・6エリアのランキング比較に必要なデータを提供していない
- 画面は現在 `player.power` を使った「戦力バランス」カードを描画している。これは秘境の試練スコアの代替にしてはならない

### ランキング取得・保存経路
- `src/index.js` の `KINGDOM_RANKING_BOARDS` に `mystic_trial` と6エリアのboard名が定義されている
- `src/mightpulse.js` にプレイヤーの `include=ranks` を要求する `getMightPulsePlayerRanks()` が存在する
- `src/ranking-store.js` の `player_rank_snapshots` 保存処理は、`mystic_trial`, `mystic_rank`, `leaderboards_json` を保存する
- `leaderboards_json` には `ranks.leaderboards` 配列が入る。ただし、この配列に6エリアそれぞれの実スコアが含まれているかはコード上の型・保存処理だけでは確定できない
- `kingdom_ranking_current` と `ranking_snapshots` は王国単位のboardランキング経路に使われている。広範囲な `ranking_snapshots` 読み取りを比較ページに追加してはならない

## 4. 未確認事項（実装前に必須）

1. MightPulseの実レスポンスで `ranks.mystic_trial` がスコアなのか順位なのか、また `mystic_rank` との意味の違い
2. `ranks.leaderboards` の実際の要素構造、6エリアのboard ID、スコア・順位・時刻のフィールド
3. `mystic_trial` および6エリアの値がプレイヤー単位で提供されるのか、王国ランキングboardから順位を逆引きする必要があるのか
4. 各boardの更新日時とデータ鮮度を正しく示せるか
5. ユーザーの権限設定でランキング情報が見えない場合の挙動
6. 既存データの保存先・履歴モード（D1/R2）で最新値を低コストに読める経路

この項目は実データ/APIレスポンスを確認するまで確定扱いにしない。必要なレスポンスは、秘密情報を除いた既存の観測データまたは安全なコード経路から調べる。Production APIの副作用を伴う試験や本番デプロイは行わない。

## 5. 推奨データ契約（UIとAPIの境界）

比較UIが個別のAPI生レスポンスを直接推測解釈する設計は避け、比較APIで正規化する。

各プレイヤーについて:
- `governor_id`, `nick_name`, `avatar_url`, `kid`
- `overall`: `score`, `rank`, `observed_at`, `source_observed_at`, `status`
- `boards[board_id]`: 同じ形式の `score`, `rank`, `observed_at`, `source_observed_at`, `status`
- `status` は少なくとも `available`, `missing`, `stale`, `forbidden`, `error` を区別する

重要:
- scoreとrankは別フィールド。片方をもう片方に代入しない
- 数値0と未取得を区別する
- 時刻がない場合は推定時刻を作らない
- 元データ時刻とEagleEye保存時刻を混同しない
- データが揃っていない比較で「勝者」を断定しない

## 6. 取得・保存・表示の設計方針

1. 最初に既存のプレイヤー観測payloadと保存済みランキング履歴の形を監査する
2. すでに保存されているデータを優先して使い、1画面表示のたびに全boardを取り直さない
3. 不足データだけを必要なAPI Pool経由で取得する。プレイヤーごとの直列更新が必要なら、進捗とタイムアウトを明示する
4. 取得結果は既存の正規化・保存処理を再利用する。重複保存・不要なD1書き込みを避ける
5. 最新データの取得に失敗しても、直近の保存済みデータがあれば鮮度表示付きで残す
6. D1 readsを抑える。比較人数×board数のたびに全履歴を走査しない
7. 広範囲の `ranking_snapshots` クエリを復活させない。必要な最新値は対象ID・対象boardに限定する
8. 既存のAPI Pool、ロール認可、サービス使用量トラッキングを維持する

## 7. 実装フェーズと完了条件

### Phase 0 — データ契約監査
- 実レスポンス/保存データからフィールドと意味を確定
- スコア、順位、board ID、時刻のマッピング表を完成
- 未確定フィールドを一覧化
- 完了条件: 7項目（総合＋6エリア）について、実際に取得可能な値と取得経路を証拠付きで分類

### Phase 1 — API整備
- `/api/player-compare` を正規化データ契約に変更
- 既存保存値優先、必要時だけ不足データを取得
- タイムアウト、部分成功、失敗理由、鮮度を返す
- 完了条件: 2〜4人、欠損・権限不足・古い値・API失敗のテストを通過

### Phase 2 — UIを新規構築
- 旧戦力バランス表示を主画面から除外
- 総合チャート＋6カード＋追加ランキング選択
- 2〜4人対応、スマホ優先、色統一、カウントアップ、発光・火花
- 完了条件: スコア未取得時もレイアウトが崩れず、架空の値を表示しない

### Phase 3 — 性能・回帰確認
- D1 reads/writes、API Pool消費、取得時間、失敗率を比較
- 既存の認証・権限・ウォッチリスト遷移を確認
- 完了条件: 重い履歴スキャンなし、処理状態が画面で追跡でき、既存機能を壊さない

### Phase 4 — リリース判断
- テスト結果と差分を確認後にマージ
- 本番デプロイは明示的に別工程として扱い、成功を確認するまで完了と表現しない

## 8. やらないこと

- 戦力・装備値・ペット値などを混ぜて秘境の試練の独自総合点を作る
- 順位をスコアとして表示する
- 実在を確認できないフィールド名を推測して実装する
- `ranking_snapshots` の広範囲スキャン
- 本番データを変える試験、本番デプロイを調査段階で実施する
- Previewをユーザー確認の代替にする

## 9. 調査時点の結論

**UIをゼロベースで再構築する方針は確定可能。一方、実スコアの完全なデータ契約は未確定。**  
最初の作業は見た目のコーディングではなく、保存済みの実データ/API契約を特定すること。そこが確定してからAPI、UIの順で実装する。
