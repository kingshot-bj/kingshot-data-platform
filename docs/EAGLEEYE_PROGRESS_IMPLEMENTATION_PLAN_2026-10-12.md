# EagleEye 全機能進捗表示 実装台帳・計画 — 2026-10-12

## 目的
全ページ共通の進捗UIを維持しながら、各機能の実際の処理状況を正しく表示し、可能な機能では残り時間を推定する。機能別のUIを乱立させず、共通の進捗管理仕様へ集約する。

## 運用上の必須制約
- 通常の実装変更は最初から GitHub `main` に直接反映する。Previewをユーザー検証手順として案内しない。
- main反映、本番デプロイ、iPhone Safari実機確認は別々の状態として記録する。
- D1 Freeの読み取り量を最優先する。`ranking_snapshots` の広範囲取得クエリを復活させない。
- 進捗の更新ごとにD1へ書き込まない。可能な限りクライアントメモリ内で管理し、既存ジョブ状態がある場合は再利用する。
- 既存の王国ウォッチリスト進捗UIの構造・見た目・進捗バーと統一し、同じ意味の表示を重複実装しない。
- 進捗率・残り時間は根拠がある場合だけ表示する。推定値は「約」「推定」を付け、確定値のように扱わない。
- エラー、拒否、キャンセル、タイムアウト、ページ離脱で進捗が残留しないことを確認する。
- 「コード上の実装あり」は動作確認済みを意味しない。未検証を完了扱いにしない。

## 現状
- 共通インジケーターは `applyEagleEyeTheme()` から各HTMLページに注入される。fetch、Response本文読取、ReadableStream reader、async iterator、XHR、同一オリジンのリンク/フォーム遷移を追跡する。
- 共通インジケーターは通信/遷移の開始と終了・経過時間は分かるが、業務処理の総件数や完了工程は原則知らない。そのためグローバルUI単独では正確な進捗率・ETAを計算できない。
- `jobProgressHtml()` の王国ウォッチリスト更新表示はランキング取得件数とプレイヤー取得カーソル等を持つため、工程別ETAを表示する実装がある。
- 進捗UIの共通スクリプトはV8構文チェックと疑似環境の部分テストを実施済み。ただしiPhone Safariの実機検証は未完了。
- 直近の `src/index.js` blob（台帳作成前の調査基準）: `368b9df0c4221513db9fd3c47cce453668133aa1`
- 本番デプロイ確認はコード反映と分離して管理する。

## 進捗表示の標準データ契約（提案）
機能側が共通UIに以下の情報を渡す。既存データで得られる項目は再利用し、新しいD1書き込みを必須にしない。
- `operationId`: 同時実行を区別するID
- `feature`: プレイヤー検索、詳細取得、ランキング等の機能識別子
- `phase`: 現在の処理工程
- `completed` / `total`: 意味が明確な場合のみ設定
- `status`: running / success / error / cancelled / timeout
- `startedAt`: 計測開始時刻
- `updatedAt`: 最終更新時刻
- `message`: ユーザー向け短文
- `etaSeconds`: 推定根拠があり信頼できる場合のみ設定。根拠がなければnull。
- 複数APIを並列実行する場合は、完了数をPromiseの終了数等で数える。ただし各APIの返却内容・必須/任意の区別を無視して「全体進捗」と称さない。
- 進捗更新はクライアント内の状態更新を基本とし、ジョブの再開・別端末からの確認等に必要な長時間ジョブのみ既存の永続状態を利用する。

## 2026-10-12 追加コード追跡：プレイヤー検索・詳細取得

### 確認できた実装経路
- `/players` は `renderPlayerSearchPage()`。検索語 `q` がある場合はサーバー側でD1の `players` を検索し、最大30件を返す。
- 検索結果は `/player?governor_id=...` へ遷移する。
- プレイヤー画面の「基本情報を更新」は `/player?governor_id=...&refresh=1`、「詳細情報を取得」は `/player?governor_id=...&rich=1` への通常のページ遷移。
- `handlePlayerApi()` は既存プレイヤーと最新Observationを読み、キャッシュにない場合・refresh指定時・richデータ不足時に `fetchPlayerThroughApiPool()` を実行し、`materializePlayer()` で保存/反映する。
- `handlePlayerRefresh()` も `fetchPlayerThroughApiPool()` → `materializePlayer()` → 使用記録という処理経路を持つ。
- プレイヤー画面HTML生成では、取得処理がサーバー側レンダリング中に行われる経路がある。共通インジケーターはリンク遷移開始を検出できるが、サーバー側の内部工程や完了件数はブラウザに届かない。

### 実装上の重要な判断
- 今のページ遷移方式を維持したまま、サーバー内部の進捗をブラウザに逐次表示することは原理上難しい。HTMLレスポンスが返るまで工程情報が届かないため。
- 正しい工程表示を実現する案は2つ:
  1. **小さく始める案**: 遷移インジケーターの文言を `基本情報を更新中…` / `詳細情報を取得中…` に区別し、残り時間は表示しない。実際の進捗を偽らない。
  2. **本格対応案**: プレイヤー画面を維持したままクライアントからJSON APIを呼び、`/api/player?governor_id=...&refresh=1` または `rich=1` を実行。完了したらデータを再表示/ページを更新する。サーバーAPIは現状、内部工程の途中経過をストリームで返さないため、当初は「基本情報を取得中」「詳細データを取得中」という段階表示と総処理時間の計測から始める。複数の下位APIの完了数を表示するには、サーバー側の工程イベント設計が別途必要。
- 既存の `handlePlayerApi()` には、API Pool呼出し前後・D1読取/Materialize・権限フィルター等の段階がある。ただし外部API内部の実進捗やETAは分からない。MightPulseの応答待ち時間を、取得済み件数のように表示しない。
- この改修はページ遷移から非同期操作へUI動作を変えるため、次のコード変更前に、対象画面の初期表示とrefresh/richのエラー表示・履歴・権限の挙動を保つ必要がある。

### 次の作業順
1. `renderPlayerPage()` の初期読込経路と `/api/player` の返却payloadの差を確認し、クライアント側更新で必要なデータが揃うかを照合する。
2. 最小差分でrefresh/richリンクを非同期操作にできるか判断。移行時に既存ページ内容を壊すリスクが高ければ、まずラベル識別だけを共通進捗に接続。

## 2026-10-12 追加監査：VIP判定と初期ロードの並列実行

### 発見
- `GET /api/me/vip` は単純な読み取りだけでなく、`evaluateVipEligibility()` を呼び、Mighty確認済みキーの有無に応じてユーザーロールをVIPへ昇格、またはVIPからADVANCEDへ降格する。
- 初期ロードでは `GET /api/me/advanced` と `GET /api/me/vip` が同時実行される。`advanced` 側がロール更新前の値を返し、`vip` 側が更新後の値を返す競合があり得る。画面の主ロール表示が `advanced.role` だけを採用すると、同じ画面内で古いロールを表示する可能性がある。
- VIP資格はユーザー本人の登録済みMightPulseキーのうち、`mighty_capable=1` かつ `mighty_check_status='CONFIRMED'` のキーが1本以上あることを基準にする。キー本数の下限や「何本Mightyか」はVIP判定条件ではない。ADMIN/OWNERはロールを維持し、確認済みならMighty機能利用を許可する。
