# EagleEye プレイヤー比較・ランキングデータ再調査 — 2026-10-13

## 目的

プレイヤー比較で円形グラフ表示とユーザー設定を設計する前に、KingShotのゲーム内ランキングが何を表しているか、MightPulseから何を取得する想定か、EagleEyeの既存コードがどこまで扱っているかを整理する。次スレッド・後続実装で誤解を繰り返さないための基準文書。

## 最重要の認識（ユーザー説明を優先）

- **領主装備・領主宝石・英雄育成・ペット等の個別ステータスを、MightPulseから直接取得できることを前提にしない。**
- ユーザーが比較したいのは、それらを反映したゲーム内の各ランキング値。たとえば「秘境の試練」内のランキング群が、それぞれ戦闘関連の育成・強さを比較する手掛かりになる。
- よって、プレイヤー比較の中心は、ゲーム内ランキングの各項目の値・順位を横並びに比較すること。装備の個別レベルや直接取得できるか未確認の内部ステータスを、別途取得できるかのように設計しない。
- 「秘境の試練」のランキングはバフ値そのものや完全な戦闘力の測定値とは断定しない。各ランキングが示す実際の項目・ルールを確認して表示する。
- **総力は戦闘力そのものではない。**兵士数などによって総力が高くなっても、行軍上限があるため、そのまま戦闘の強さとはみなせない。総力は参考情報に分離する。
- VIP、座標、プロフィール情報はプレイヤー詳細向けであり、戦闘比較の主要グラフに混ぜない。
- UIは小さめの円形グラフを2列程度で複数並べ、1画面で複数項目を視覚比較できるようにする。ユーザーは表示項目・順番等を設定で変更できるようにする。ただし、実データが確認できる項目だけを表示対象にする。

## ソースコードで確認できた事実

### 1. MightPulseの取得経路

- `src/mightpulse.js` の `getMightPulsePlayer()` は `/players/{governor_id}?include=...` を呼ぶ。
- `src/data-collection-engine.js` の `collectPlayerDetail()` は `include=base,heroes,ranks,gov_gear` で取得する。
- `getMightPulsePlayerRanks()` は `include=ranks` を使う。
- したがってコード上、基本情報・英雄情報・本人ランキング・領主装備データを要求する経路は存在する。ただし、これは要求パラメータとコードの存在を確認しただけで、各フィールドがAPIレスポンスに含まれること、全プレイヤーで取得成功すること、比較API/UIまで届くことを保証しない。
- 今回、実際の本番MightPulseレスポンスや本番D1/R2保存データを直接参照する権限・経路は利用できていない。実データの内容・充足率は未確認と記録する。

### 2. ランキングのデータモデル

既存の `docs/mightpulse-ranking-data-map.md` では、プレイヤーの `include=ranks` に次の項目が含まれる仕様を記録している。

- `power / power_rank`
- `kills / kills_rank`
- `town_center_level / town_center_rank`
- `migrant_score / migrant_rank`
- `mystic_trial / mystic_rank`
- `leaderboards[]: name / value / kingdom_rank`

また、王国ランキングAPI `/v1/kingdoms/{kid}/ranks` と、26種類のランキングボードを扱う設計が記録されている。これらは既存のAPI仕様調査文書に基づく情報であり、今回ライブAPIで再取得した結果ではない。

### 3. 既存の比較ヘルパー

- `src/player-compare.js` の `buildPlayerCompareSeries()` は、現状 `power` と `power_rank`/ランキング履歴を時系列化する。
- 同ファイルに領主装備・宝石・ペット等の比較用数値を抽出・正規化する処理は確認できなかった。
- `src/player-store.js` はプレイヤーの観測payloadを保存するが、DBの正規化列として保存する項目は主にID、名前、王国、総力、役場、VIP、座標、撃破、同盟等。豊富な情報はObservation/履歴payload側に存在する可能性があるため、正規化列の有無だけで元データ欠落と断定してはいけない。
- 比較APIが現在ランキングの各項目をどのように受け取り、画面に出しているか、実際のpayloadの例を使った端から端までの確認は未完了。

## ランキングを比較UIへ使うときのルール

1. 各ランキングを、まず「ゲーム内のランキング項目」として独立して表示する。ランキング間の値を単純加算しない。
2. 順位とスコア/値を別のデータとして扱う。順位は小さい数が上位になるため、スコアと同じ方向の円グラフに直接変換しない。
3. ランキングごとに値の意味・単位・更新条件が違う可能性がある。項目間を同一尺度に正規化した「総合戦闘力」を勝手に作らない。
4. 円形グラフは、その項目内で2人の値を比較できる尺度が定義できる場合に限る。定義できない場合は順位・値・差分の数値カードにする。
5. グラフ中央または下部に実際の値と順位、A/Bの差を表示し、円の見た目だけで優劣を誤認させない。
6. 総力は補助情報に留め、戦闘能力の代理指標として順位づけしない。
7. VIP、座標、プロフィール、同盟情報は詳細ページに置き、戦闘比較の主項目から外す。
8. 表示設定は「取得可能な項目カタログ」から生成する。データのない項目を見せかけの値で埋めない。

- 領主装備・領主宝石・英雄装備・ペットの個別値をAPIから直接取得済みだと仮定しない。
- 「秘境の試練」等のランキングが表す項目を無視して、架空の装備レベルや架空の育成点数を円にすることを禁止。

- VIP・座標を戦闘比較の主指標に混ぜない。

## 2026-10-13 追記：秘境の試練の各ランキングと育成要素の対応

### 調査結果（攻略資料に基づく対応表）

KingShotの秘境の試練は、エリアごとに異なる育成要素が遠征戦闘の結果へ反映される構成として攻略資料で説明されている。EagleEyeの比較機能では、これを**育成要素の直接数値ではなく、その要素が関係するコンテンツのランキング指標**として扱う。

| 秘境の試練のエリア | 比較対象として対応づける育成要素 | EagleEyeでの扱い |
|---|---|---|
| 闘技場（Coliseum） | 英雄、英雄装備、英雄専用ウィジェット | 英雄系の参考指標 |
| 生命の森（Forest of Life） | ペット、ペットスキル | ペット系の参考指標 |
| 水晶鉱山（Crystal Cave） | 領主宝石（Governor Charm） | 領主宝石系の参考指標 |
| 知識の枢軸（Knowledge Nexus） | 学院研究、戦争学院研究 | 研究系の参考指標 |
| 溶岩要塞（Molten Fort） | 領主装備（Governor Gear） | **領主装備系の参考指標** |
| 輝光の塔（Radiant Spire） | 英雄・英雄装備・専用要素、ペット、領主宝石、領主装備、研究、スキン、オアシス島ボーナス、VIP等の複合要素 | 総合的な参考指標。単独カテゴリの指標として使わない |

### 解釈上の重要な制約

- 領主装備をランキング経由で比較する場合、対応先は**秘境の試練「溶岩要塞」**。領主宝石は「水晶鉱山」。
- ただし、溶岩要塞のスコアや順位は、領主装備のレベル・個々の部位の値そのものではない。該当要素が関係するコンテンツの結果・ランキングであり、部隊編成、進行状況、その他の影響要因を含み得る。したがってUI上は「領主装備の実数値」ではなく「領主装備系ランキング指標」と説明する。
- 順位とスコアは別フィールドとして扱う。順位だけの場合、1位と2位の差をスコア差と同じものとして扱わない。
- 輝光の塔は複数要素を反映するため、領主装備・ペット等の単一カテゴリの比較に流用しない。
- これは公開攻略資料に基づく対応関係であり、MightPulseが各エリアのスコアと順位を実際に返すか、EagleEyeで取得・保存・比較API・UIまで届いているかは未検証。実レスポンスで確認する。
- 日本語表示名は実際のゲーム内表示と照合して最終確定する。攻略資料の英語名を機械的に直訳して、ゲーム内表記と異なる名称を新設しない。
