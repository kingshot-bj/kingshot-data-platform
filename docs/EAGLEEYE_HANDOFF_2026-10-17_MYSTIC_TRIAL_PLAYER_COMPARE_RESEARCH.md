# EagleEye 引き継ぎ — 秘境の試練を軸にしたプレイヤー比較の再調査（2026-10-17）

## この引き継ぎの目的

プレイヤー比較の表示改善について、同じ説明を繰り返さず、これまでの調査結果・ユーザーの意図・未解決事項を次スレッドへ引き継ぐ。次の担当はこの文書と参照資料を先に読み、既出の一般論を再説明せず、未解決点の調査または具体的な設計作業から始めること。

## ユーザーが明確にしている目的

秘境の試練の6コンテンツの進捗は、単なる順位やスコアではない。プレイヤーが英雄・英雄装備、ペット、領主宝石、研究、領主装備などへどの程度育成投資しているかを推し量るための指標である。6分野の進捗を横断して見ることで、プレイヤーごとの育成傾向・相対的に遅れている分野・投資の偏りを読み解きたい。

ユーザーはこの点を複数回説明しており、同じ趣旨を再度説明することに強い不満を示している。次の応答では「6項目を育成プロフィールとして表示する」という既出の提案を繰り返すだけにしないこと。既存コード・既存調査資料・実際のAPIデータを読み、何がまだ調査されていないかを特定し、具体的な新しい結論を出すこと。

## 6コンテンツの育成分野（攻略資料に基づく）

- Coliseum：英雄・英雄装備
- Forest of Life：ペット
- Crystal Cave：領主宝石（Governor Charm）
- Knowledge Nexus：学院・戦争学院の研究
- Molten Fort：領主装備
- Radiant Spire：複数の育成要素を組み合わせた総合的な戦闘構成。ほかの項目と異なり兵士も使用する

参照資料：docs/EAGLEEYE_PLAYER_COMPARE_FIXED_BENCHMARKS_2026-10-14.md。同資料は攻略資料 https://kingshotmastery.com/guides/mystic-trial を参照している。

この分類は「どの育成分野が関係するか」を示すものであり、ステージだけから個別の英雄装備レベルやペットレベルを断定するものではない。育成要素の直接的な値がAPIにある場合は、その実データと照合して説明する。

## コードを読んで確認済みのこと

- 比較ページの実装は src/index.js 内の renderPlayerComparePage()。
- グラフ補助実装は src/player-compare-enhancements.js。
- 画面には比較バー、レーダー、数値などの表示モードがある。
- ステージ表記を持つランキングは数値グラフから除外され、ゲーム内表示値で比較する案内がある。
- 既存画面には英雄・英雄装備・専用装備・領主装備の情報を比較するための基盤もある。
- 比較APIは既存Observationを利用する方針。比較のためだけの追加MightPulse取得を増やさず、D1 Free読み取りの増加を避ける。ランキング履歴取得をむやみに復活させない。
- 順位は王国内の母集団に依存する。異なる王国の順位を強さの直接比較や総合スコアに変換しない。

## 数値・ステージ表記について確定していないこと

参照：docs/EAGLEEYE_PLAYER_COMPARE_FIXED_BENCHMARKS_2026-10-14.md

- MightPulse公開APIの説明では ranks.leaderboards[] に name / value / kingdom_rank があるが、秘境の試練の各 value の式、単位、上限値、カテゴリー別基準値は説明されていない。
- 公開プロフィールに見える約10,000〜60,000の値はカテゴリー識別オフセットの可能性があるが、差し引いてよいと確定していない。
- ステージ表記（例：95-2）を内部値から復元する式・その比較上の扱いは、公式仕様として確定していない。
- 選択中のプレイヤー内で最大値を100%にするレーダーは、比較対象を変えるだけで形が変わるため、固定基準値が検証されるまでは採用しない。
- 異なるコンテンツ間で進捗値を足し合わせたり、推測した割合・総合育成スコアを作ったりしない。

## 次に調査すること（既出提案の反復ではなく、実データに基づいて進める）

1. Probeで保存済みのRaw JSON / Observationを使い、6項目それぞれについて name, value, value_label, kingdom_rank と画面上のステージ表記を照合する。必要なら既存サンプルを複数プレイヤーで比較する。API呼び出しは追加しない。
2. 既存の6項目の値が「ステージ進捗として比較可能な表記」なのか、「内部符号化値」なのか、現在のコードがどのフィールドをどの順で表示しているかを具体的に追跡する。
3. ステージ表記を直接比較する場合の安全な差分ロジック（同一コンテンツ内だけで比較、ステージとサブステージを適切に順序比較、欠損・100+・古い観測値を別扱い）を、データサンプルと既存コードから検証する。根拠が足りない部分は未確定と明記する。
4. 6項目の進捗と実際の英雄装備・領主装備・ペット等のデータが、どこまで同一Observation内で取得できるかを確認する。分野の関連づけをUIに出す際、直接確認できた情報と推測を明確に分ける。
5. 上記の調査結果から、現行UIより有用な比較表現を具体化する。提案だけを繰り返さず、既存コードのどこを変えるか、どのデータでどう検証するかまで示す。設計確定前のコード変更・デプロイはしない。
