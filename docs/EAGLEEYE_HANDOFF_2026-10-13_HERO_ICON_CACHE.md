# EagleEye 引き継ぎ｜英雄アイコンの段階的収集・保存

作成日：2026-10-13

## 対象
- GitHub: https://github.com/kingshot-bj/kingshot-data-platform
- ブランチ: main
- 英雄カタログ: `src/hero-catalog-page.js`
- 英雄スキル辞書: `src/hero-skills-ja.js`
- ルーティング・既存プレイヤー英雄表示: `src/index.js`
- R2アーカイブ: `src/r2-archive.js`
- 現在の本番URL: https://kingshot-data-platform.black-jack-kingshot.workers.dev

## ユーザーの合意
英雄アイコンを、可能なら英雄ごとに一度だけ取得・保存し、その後は英雄カタログや他の画面で共通利用する方針で進める。
全英雄を一気に取得する必要はなく、順次・段階的に収集してよい。
不明な画像や英雄対応は絶対に推測で補完しない。見つからない場合は未取得・未確認として残し、必要ならユーザーがゲーム内で確認する。
本番Workerへのデプロイは、ユーザーから明示的に依頼されるまで行わない。

## これまでの調査結果
1. ユーザー提供の実機スクリーンショットでは、アマデウス、ローザ、マーゴ等の英雄アイコンが実際に表示されている。つまり、少なくとも画面描画時点では画像が取得・参照できている。
2. 表示されることと、画像本体を恒久保存していることは別。現状、英雄アイコン画像本体の恒久保存はコード上で確認できていない。
3. `src/hero-catalog-page.js` は現在、英雄名の頭文字を表示するプレースホルダーを使用している。実際の英雄画像はまだ組み込まれていない。
4. `src/index.js` の既存プレイヤー英雄表示では `hero.icon` を利用し、`normalizeProfileAssetUrl(value)` でURLを正規化する既存処理がある。既存経路の画像URLを優先して再利用すること。
5. `migrations/0002_api_observations.sql` の `api_observations.payload_json` はAPIレスポンスを保存する仕組み。過去データに英雄情報・画像URLが入っている可能性はあるが、実データを見て確認できていない。
6. `src/player-store.js` はプレイヤー情報を保存し、`src/r2-archive.js` はプレイヤー履歴のR2保存処理を持つ。ただし、これらが英雄アイコン画像ファイル本体を保存しているわけではない。
7. `wrangler.jsonc` ではD1 binding `DB`、R2 binding `ARCHIVE` が定義されている。D1はメタデータ、R2は画像ファイル本体の保存候補。ただし、既存のR2アーカイブ構造に画像専用保存を混ぜず、キー設計とアクセス方法を別途設計すること。
8. リポジトリ内の画像一覧には主に `public/assets/eagleeye/bjnyan/` 以下のEagleEye/BJにゃん画像があり、KingShot全英雄のポートレート画像群は確認できなかった。
9. 既存の `scripts/collect-hero-gear-assets.mjs` と `.github/workflows/hero-gear-assets.yml` は英雄装備画像向けであり、英雄アイコン収集とは別物。Actions成果物の保持期間は7日間の設定。
10. 英雄スキル辞書は37英雄を対象に調査しているが、この37はスキル辞書監査の収録対象であり、ゲーム内の全英雄数と同一と断定しない。

## 実装方針
- まず既存コードと利用可能な保存データを調査し、`hero.id` / 英雄名 / `hero.icon` URLの実データ構造を確定する。
- 既存の取得済みデータから英雄とアイコンURLを抽出できるなら、新規API取得を増やす前にそれを再利用する。
- 英雄ごとに安定したキー（可能なら英雄ID。IDがなければ確実な識別子が見つかるまで仮の名前一致に依存しない）で対応表を持つ。
- R2に画像本体、D1に英雄ID・名前・保存先キー・状態・取得日時・ソースURLなどのメタデータを保存する案を検討する。スキーマは既存設計と整合するか確認してから追加する。
- 画像取得はキューや小さなバッチで段階的に実施し、失敗時のリトライ・重複防止・同時実行制御を備える。既存MightPulse APIを英雄ごとに大量再取得する設計は避ける。
- 既にR2保存済みなら再取得しない。URLが変わっても無条件に上書きしない。
- 画像が見つからない英雄は未取得・未確認として表示し、別英雄の画像を代用しない。
- 英雄カタログのカードに実際のアイコンを組み込み、画像がない場合は現在のプレースホルダーをフォールバックとして残す。
- 画像の利用元・利用条件・キャッシュ可能性を確認する。URLが取得できるだけで恒久保存・再配布が許可されているとは断定しない。
- 実装後はローカル/CIテストとデータ整合性確認を行う。本番デプロイはユーザーの明示指示まで行わない。

## 次スレの最初のタスク
1. `src/index.js` の `normalizeProfileAssetUrl`、プレイヤー英雄表示、MightPulseプロフィール取得・保存経路を読み、英雄アイコンURLがどのレスポンスに由来するか追跡する。
2. D1/R2の実データを安全に確認できる既存診断/API/接続手段があるか調べる。接続できなければ「未確認」と明記し、取得済みと推測しない。
3. `api_observations.payload_json` に英雄情報が入る実装条件をコードから確認し、保存済みデータを再利用する可能性を評価する。D1 Free Tierを意識し、全履歴の広範な読み取りを避ける。
4. 英雄ID・名前・画像URLの対応表と、保存対象英雄の収集状態を設計する。
5. 小さく安全な実装案を作り、コード変更・テストまで進める。進捗は長時間作業なら10%刻みで報告する。

- 画像を「画面に表示できる」ことだけを根拠に「保存済み」と言わない。
- ユーザーの実機画面に表示された英雄アイコンは、既存経路から取得可能な実例として扱う。

- D1の広範囲読み取りを復活させない。
